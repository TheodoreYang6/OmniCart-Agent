### 每个阶段的技术细节标注（小字灰色，在对应方块下方或侧边）

**① 搜索词构建：**
- 快速路径：Router 产出 category + must_tags 非空时，直接拼接 `user_query + category + sub_category + spec_keywords`，跳过 LLM，省 ~600ms
- 慢速路径：调用 qwen-turbo 做关键词改写，"推荐蓝牙耳机"→"蓝牙耳机 真无线耳机 降噪 高音质 500元"，结果 Redis 缓存 30min
- 追问场景品类已锁定时走快速路径

**② Embedding 向量化：**
- text-embedding-v4 将搜索词映射为 1024 维浮点向量
- 失败降级：jieba 关键词提取 → 子串匹配计数（不依赖向量）
- 分块检索与产品级检索共用同一 query 向量

**③ 双集合检索：**
- `product_chunks` 集合（~800条）：优先检索。每件商品拆为 summary×1 + mkt×1 + faq×N + rev×N，每块独立 Embedding。chunk 级命中后按 product_id 分组聚合（max_score 或加权平均），chunk 权重：summary=1.0, faq=1.0, mkt=0.9, rev=0.8
- `products` 集合（105条）：降级补齐。当分块聚合结果不足 top_k 时，用产品级检索补齐
- 两个集合均为 1024 维 COSINE 距离，payload 冗余品类/价格字段，块级别即可过滤无需回查 DB
- Qdrant 不可用 → 本地 Embedding 缓存 JSON（105 条暴力余弦）→ 还不行 → 纯文本关键词子串匹配

**④ 多维过滤：**
- 品类硬过滤：`category` 不匹配 → 直接移除
- 价格硬过滤：`price > budget_max` → 移除（但保留在结果中标记，不丢失信息）
- 子品类放宽：sub_category 检索无结果 → 自动设为 `None` 重试（Router LLM 提取的子类标签可能与数据集不完全一致）
- 视觉置顶：拍照识图高置信度（≥0.5）匹配到的商品 → 强制设 reranker_score = 0.99，不被后续评分翻盘
- 避雷硬过滤：用户偏好中的 avoid_tags 匹配标题/品牌 → 从检索结果中直接移除

**⑤ Reranker 语义精排：**
- 每个候选商品构建结构化文档：title + category + sub_category + 营销描述(300字) + FAQ(前2条) + 评论(前2条) + 证据片段(前2条)
- 调用 qwen3-rerank，传入 query + documents[]，返回 `{index, relevance_score}` 排序
- 分数校准：`calibrated = 0.68 + 0.38 × raw_score`，将压缩在窄区间的原始分映射到商业可读的 0.68~1.06
- 执行条件：候选商品 > 1 且非快速模式。仅 1 个商品或快速模式 → 跳过，省 ~300ms
- 异常降级：Reranker API 不可用时 `except Exception: pass`，保持检索原始排序，不阻塞链路

**⑥ 三通道证据补充：**
- Text 通道（主，先执行）：embedding 语义搜索 → 产出 products[] + 营销证据 E-MKT-{pid}-{i}
- Review 通道（并行）：遍历已检索商品评论区，≤2★→risk(0.8/0.5), 3★→neutral(0.4), ≥4★→positive(0.7)，产出 R-{pid}-{i}
- Policy 通道（并行）：遍历 Top3 商品的 official_faq，每条 FAQ → policy_faq (confidence=0.9)，产出 POL-{pid}-{i}
- Review 和 Policy 通过 ThreadPoolExecutor(max_workers=2) 并行执行
- 补充通道（条件触发）：主检索结果 < 3 件时，用分块 Embedding 余弦相似度反向发现被遗漏的商品，产出 E-SUPP-{pid}

**⑦ 上下文编译：**
- Top 3 商品（有视觉结果时 Top 5），每商品仅标题 + 品牌 + 价格 + reranker 匹配度描述
- 每商品 ≤ 1 条证据摘要，≤ 100 字，过滤掉"余弦相似度:0.xxx"等无意义内容
- 不传完整 product JSON / reviews / FAQ 列表 → 控制 Prompt 在 ~250 token
- 注入 FollowUpEngine 上下文提示 + 视觉识别结果（如有）+ 用户约束信息
- 完整 Prompt 写入 `data/audit_prompts.log` 供离线审计

**⑧ 流式生成 + Guard：**
- 4 条生成路径：闲聊→独立 Prompt / 快速模式→模板秒回 / 无结果→诚实告知 / 正常→LLM 流式
- LLM 生成：qwen-turbo, 6s 超时 → asyncio.wait_for → 超时/异常 → 结构化模板兜底
- 幻觉校验：`_answer_cites_products` 验证回答是否包含候选商品品牌/标题片段 → 不通过回退模板
- Guard 5 项检查：evidence_bound / price_accurate / risk_warned / honest_on_empty(硬) / hallucination(硬)
- SSE 协议：event:token→逐字推送 / event:result→结构化结果 / event:done→结束 / event:error→异常

### 右上：RAG 生成评测 — 3 项 LLM-as-Judge 指标

**测什么：** 检索评测只回答了"捞没捞到"，无法回答三个更深层的问题：生成的回答有没有编造不存在的信息？检索到的文档有多少是真正相关的？回答所需的关键信息是不是都在检索结果里？

**数据集：** `data/rag_eval_dataset.json` — 105 条人工标注 Golden Query，覆盖全部 4 品类、23 个子品类，关联 98 件商品。

| 品类 | Query数 | 覆盖子品类 |
|------|:--:|------|
| 数码电子 | 32条 | 智能手机/笔记本/平板/耳机/充电宝/充电器 |
| 美妆护肤 | 26条 | 精华/化妆水/面霜/防晒/洁面/蜜粉/唇釉/眼霜/卸妆/粉底液/面膜/眉笔 |
| 服饰运动 | 25条 | T恤/速干T恤/运动长裤/卫衣/跑步鞋/篮球鞋/徒步鞋/瑜伽裤/户外裤/背包/帽子/运动短裤 |
| 食品饮料 | 22条 | 咖啡/茶饮/碳酸饮料/功能饮料/牛奶/酸奶/坚果零食/方便食品/调味品 |

每条标注三个字段：
- `relevant_product_ids`: 人工判定相关商品 ID（用于 Context Precision / Recall@K）
- `relevance_grades`: 相关度分级 0~3（用于 NDCG@K）
- `key_info_points`: 回答应覆盖的关键信息点（用于 Context Recall）

**三项指标详解：**

```
┌─────────────────────────────────────────────────────────────────────┐
│  Faithfulness (忠实度)                                              │
│  ─────────────────                                                  │
│  测量：生成的回答中的事实声明，能否在检索到的证据中找到支撑            │
│                                                                     │
│  计算方式（LLM-as-Judge）：                                          │
│  1. LLM 从生成回答中提取所有事实声明 (claims)                         │
│  2. 逐条验证每个声明是否能在检索上下文中找到依据                       │
│  3. Faithfulness = 有支撑的声明数 / 总声明数                         │
│                                                                     │
│  例：回答"QCY MeloBuds ANC 降噪深度 40dB，续航 30 小时"              │
│  声明1"降噪深度40dB" → FAQ中Q:降噪深度? A:40dB → ✓有支撑             │
│  声明2"续航30小时" → 检索上下文中无此信息 → ✗无支撑                  │
│  Faithfulness = 1/2 = 0.50                                         │
│                                                                     │
│  代码：eval/rag_metrics.py:compute_faithfulness(answer, context)      │
│  当前得分：≈ 0.91                                                    │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│  Context Precision (上下文精准度)                                     │
│  ─────────────────────────                                          │
│  测量：检索回来的文档中，有多少是真正与问题相关的 (rank-aware)          │
│                                                                     │
│  计算方式：                                                          │
│  AP = Σ(P@k × rel@k) / total_relevant                               │
│  其中 P@k = 前k个文档中相关的比例，rel@k = 第k个文档是否相关(0/1)      │
│                                                                     │
│  例：检索返回 [P001(相关), P003(不相关), P005(相关)]                   │
│  P@1=1/1=1.0, P@2=1/2=0.5, P@3=2/3=0.67                            │
│  AP = (1.0×1 + 0.5×0 + 0.67×1) / 2 = 0.835                         │
│                                                                     │
│  rank-aware 意味着：相关文档排得越靠前，分数越高                       │
│                                                                     │
│  代码：eval/rag_metrics.py:compute_context_precision(query, context,  │
│        relevant_ids)                                                 │
│  当前得分：≈ 0.86                                                    │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│  Context Recall (上下文召回率)                                        │
│  ─────────────────────────                                          │
│  测量：回答所需的关键信息点，是否全部在检索上下文中找到                │
│                                                                     │
│  计算方式（LLM-as-Judge）：                                           │
│  1. 从标注数据中读取 key_info_points（如"降噪深度""价格""续航"）       │
│  2. LLM 逐条检查每个信息点是否在检索上下文中被覆盖                     │
│  3. Context Recall = 已覆盖的信息点数 / 总信息点数                    │
│                                                                     │
│  例：query="推荐降噪耳机500以内"                                      │
│  标注的 key_info_points: ["降噪深度", "价格<500", "蓝牙版本"]         │
│  检索上下文覆盖了"降噪深度"和"价格<500"，缺"蓝牙版本"                  │
│  Context Recall = 2/3 = 0.67                                        │
│                                                                     │
│  代码：eval/rag_metrics.py:compute_context_recall(key_info_points,    │
│        context)                                                      │
│  当前得分：≈ 0.82                                                    │
└─────────────────────────────────────────────────────────────────────┘
```

#### 维度 1: Relevance 语义相关度 (权重 0.45)

**源码：** `scoring.py:_calc_keyword_match` (line 334-372)

**取值优先级链：**

```
force_rag_relevance > 0?     ← EvidenceScoringHelper 产出
  ├─ YES → 直接使用          ← 来自 reranker_score > retrieval_score > chunk_score
  │                            (ENABLE_EVIDENCE_SCORING=true 时走这条路)
  ├─ NO → llm_relevance > 0? ← LLM 评估器产出
  │   ├─ YES → 使用           ← (ENABLE_DECISION_LLM=true 时，默认关闭)
  │   └─ NO → keyword_score   ← fallback 到关键词匹配
  │
  ▼
keyword_score 的分数类型自动检测:
  if score ≤ 0:    kw_norm = 0.62                          # 无分数→基线
  elif score < 1.0: kw_norm = 0.68 + 0.38 × score         # 余弦相似度/Reranker分→校准
  else:            kw_norm = 0.62 + 0.28 × log10(score)   # 旧关键词命中数→对数映射
```

**CJK Bigram 子品类加成（中文特化）：**

```python
has_cjk = any('一' <= c <= '鿿' for c in query_lower)
if has_cjk:
    for i in range(len(query_lower) - 1):
        bigram = query_lower[i:i+2]       # 2-gram 滑动窗口
        if bigram in sub_category_lower:   # 命中子品类名
            sub_bonus += 0.10              # 每命中一个 +0.10
sub_bonus = min(0.20, sub_bonus)           # 封顶 +0.20

relevance = min(1.0, kw_norm + sub_bonus)
```

**为什么用 Bigram：** CJK 语言中二字词是最小语义单元。query"蓝牙耳机"中"耳机"命中子品类"真无线耳机"→ 说明 query 和品类高度相关。

**实例：** 用户搜"降噪耳机"
- Reranker 给 QCY MeloBuds ANC 打分 0.72
- 走 EvidenceScoringHelper → force_rag_relevance = normalize(0.72) = 0.72
- sub_bonus: "耳机" bigram 命中 "真无线耳机" → +0.10
- 最终: relevance = 0.72 + 0.10 = 0.82

#### 维度 2: Budget Fit 预算匹配 (权重 0.20)

**源码：** `scoring.py:_calc_budget_fit` (line 378-398)

```python
if budget_max is None or budget_max <= 0:
    return 0.98                              # 无预算约束→近乎满分，不影响排序

price = product.base_price

if price <= budget_max:                      # 预算内
    ratio = price / max(budget_max, 1)
    if ratio < 0.3:   return 0.98           # 远低于预算→性价比高
    elif ratio < 0.6: return 0.93            # 适中
    else:             return 0.92            # 接近上限

else:                                        # 超出预算
    overage = (price - budget_max) / budget_max
    if overage < 0.2:   return 0.80          # 轻微超出(≤20%)
    elif overage < 0.5: return 0.60          # 明显超出(20%~50%)
    else:               return max(0.0, 0.45 - overage)  # 严重超出，线性衰减
```

| ¥450 | ratio=0.90 → 0.92 | 0.92 | 接近上限 |
| ¥580 | overage=0.16 → 0.80 | 0.80 | 轻微超出 |
| ¥800 | overage=0.60 → max(0, 0.45-0.60) | 0.00 | 严重超出 |

#### 维度 3: User Sat 用户满意度 (权重 0.12)

**源码：** `scoring.py:_calc_user_satisfaction` (line 404-440)

```python
if no reviews:
    return 0.80                              # 无评论→中性基线 0.80，不惩罚

ratings = [r.rating for r in reviews]
score = avg(ratings) / 5.0

# Bayesian 连续平滑: C=3条虚拟评论, prior=0.80
# 目的: "1条5星好评 ≠ 满分" (冷启动保护)
score = (score × n + 0.80 × 3) / (n + 3)

# 评论数量微奖励 (经过市场验证的商品值得信任)
if n >= 20:  score += 0.08
elif n >= 5: score += 0.05
elif n >= 2: score += 0.03

# 好评文本关键词匹配
positive_keywords = ["推荐","好用","满意","回购","值得","不错",
                     "好评","喜欢","性价比","赞","棒"]
if count(评论含正面词) >= 3: score += 0.03

return clamp(score, 0, 1)
```

**Bayesian 平滑效果示例：**

| 真实评分 | 评论数 n | 平滑前 | 平滑后 | 变化 |
|:--------:|:--------:|:------:|:------:|------|
| 5.0 | 1 | 1.00 | **0.85** | -0.15 (防止"1条5星=满分") |
| 5.0 | 5 | 1.00 | **0.93** | -0.07 (逐步接近真实值) |
| 5.0 | 20 | 1.00 | **0.97** | -0.03 (大样本几乎不受影响) |
| 2.0 | 2 | 0.40 | **0.64** | +0.24 (极端低分向中性回归) |
| 3.0 | 3 | 0.60 | **0.70** | +0.10 (低评分被修正) |

**设计理念：条目化 vs 单行 JSONB**

传统做法每个用户一行，所有偏好塞一个 JSONB 字段。OmniCart 选择每条偏好独立 entry：

| 维度 | 单行 JSONB | 条目化 (OmniCart) |
|------|-----------|-------------------|
| 增删 | 需合并逻辑 | 独立增删，互不影响 |
| 品类隔离 | 全量加载 | 品类索引查询，精准匹配 |
| 开关 | 无法单条禁用 | 每条独立 enabled 开关 |
| 增量 | "记住我喜欢XX" → 合并 | 直接 INSERT 新条目 |

**数据模型（`user_preference_entries` 表）：**

```
  entry_id: "PREF-a1b2c3d4"     # 唯一标识
  user_id: "user_xxx"
  raw_text: "我是油皮敏感肌，喜欢资生堂和兰蔻，不喜欢韩系品牌"
  category: "美妆护肤"            # 品类索引 (查询时 WHERE category=?)
  sub_category: "护肤品"
  brands: ["资生堂", "兰蔻"]      # JSONB[]
  scenarios: []                   # JSONB[]
  budget_min: 300, budget_max: 500
  avoid_tags: ["韩系品牌"]        # JSONB[] → 检索层硬过滤 + 评分层降权
  must_tags: ["油皮肤质适用"]     # JSONB[] → search_hints 拼接
  enabled: true                   # 启用/禁用开关
```

**品类感知注入 `inject_profile_hints()`（最核心设计）：**

```python
# user_profile_service.py:inject_profile_hints (line 89-132)
category = detect_category_from_query("推荐一款蓝牙耳机")  → "数码电子"
entries = list_entries(user_id, category="数码电子")      → 仅查数码电子条目
# 不查美妆/服饰/食品条目！防止"油皮"污染"手机"搜索

if not entries:
    return {"enriched_query": query, "avoid_tags": []}    # 该品类无偏好→不注入任何东西

hints["enriched_query"] = f"{query} {must_tags} {brands}"  # → 检索召回增强
hints["context_prompt"]= "[用户偏好] 品类:数码电子 | 品牌:Sony,Apple | ..."
hints["avoid_tags"]    = [...]
```

**search_hints 与 context_prompt 分离：**

| 注入方式 | 内容来源 | 注入目标 | 影响范围 |
|----------|----------|----------|----------|
| search_hints | must_tags + brands | enriched_query（拼在 query 后面） | **直接影响检索召回** |
| context_prompt | 品牌/场景/预算/避雷 + "优先推荐偏好品牌" | state.context_prompt | **仅影响 LLM Prompt** |
| avoid_tags | 避雷标签 | constraints.exclude_tags | **检索层硬过滤** |

设计意图："户外"场景关键词放入 context_prompt 而非 search_hints——防止用户搜索"充电宝"时，"户外→便携/大容量"将充电宝挤下去而推了手机。场景词只影响 LLM 的推荐语，不影响检索召回。

**对话提取（自动发现偏好信号）：**

```python
# user_profile_service.py:has_long_term_signal (line 170-175)
_LONG_TERM_SIGNALS = ["记住", "以后都", "我一直", "永远", "长期", "保存偏好", ...]
_TEMPORARY_SIGNALS = ["这次", "本轮", "当前", "暂时", "临时", "先"]

def has_long_term_signal(message):
    return any(s in message for s in _LONG_TERM_SIGNALS) \
       and not any(s in message for s in _TEMPORARY_SIGNALS)
# "以后都推荐索尼" → True → 异步 parse_and_save
# "这次先看看索尼" → False → 不保存
```

**解析流程（Qwen LLM → 规范化 → 保存）：**

```
  用户输入: "我是油皮敏感肌，喜欢资生堂兰蔻，不喜欢韩系，预算300-500"
      │
      ▼
  _parse_with_qwen(raw_text) → Qwen LLM 返回:
    {skin_type:["油皮","敏感肌"], brands:["资生堂","兰蔻"],
     avoid_tags:["韩系品牌"], budget_min:300, budget_max:500,
     categories:["美妆护肤"]}
      │
      ▼
  _normalize_fields() → 规范化:
    skin_type["油皮"] → must_tags:["油皮肤质适用"]
    categories[0] → category:"美妆护肤"
    未知字段 → must_tags 或 avoid_tags 归类
      │
      ▼
  写入 user_preference_entries 表 (独立条目, entry_id 唯一)
```

### 左上：数据规模化 — 105 → 10,000+

**核心挑战：** 商品从百级到万级后，全量 Embedding 索引不可行，本地暴力降级不可用，数据需要持续更新。

**增量索引 Pipeline：**

```
  新品上架 → chunk 拆分 → 异步批量 Embedding → upsert Qdrant
  商品信息变更 → 受影响 chunk 重新 Embedding → 覆盖旧向量
  评论新增 → 新 rev chunk 追加 → 关联 product 聚合向量更新
```

**Qdrant 分片：** 按 category 分 4 个 shard，每 shard 独立 HNSW 索引。查询时先品类路由命中对应 shard，避免跨品类噪声。

**实时更新链路：**

```
  PostgreSQL trigger → 消息队列 → Embedding worker → Qdrant upsert
  全量 Re-index 改为增量，不再每次重建整个集合
```

**降级链升级（当前 105 条暴力余弦在万级不可用）：**

```
  Qdrant 不可用 → Elasticsearch 稀疏向量 (BM25)
       ↓
  → PostgreSQL pgvector
       ↓
  → 纯文本关键词 (最小可用)
```

### 右上：全链路延迟优化 — 3s → <1.5s

**当前延迟分布：**

| 阶段 | 当前 | 目标 |
|------|:--:|:--:|
| LLM 改写 | ~600ms | ~200ms (模型降级) |
| Embedding | ~200ms | ~50ms (本地化部署 BGE-small) |
| Qdrant ANN | ~50ms | ~30ms |
| Reranker | ~300ms | ~150ms (Top1 高分跳过) |
| LLM 生成 | ~1500ms | ~800ms (qwen-turbo→qwen-plus/流式提前) |
| **总计** | **~3s** | **~1.3s** |

**关键优化手段：**

```
  ① 模型分级: Router/改写用轻量模型, 生成用主力模型
  ② Embedding 本地化: 部署 BGE-small-zh 到服务侧, 省 API 往返
  ③ 流式提前: Decision 完成后立即 SSE 推送, 不等 Response 节点
  ④ Reranker 条件跳过: Top1 分数 > 0.9 → 省 ~300ms
  ⑤ 并行度提升: 改写 + Embedding + Profile 三路并行
  ⑥ Prompt 预编译: Router Prompt 模板预缓存, 仅替换变量
```

### 左下：视觉 & 语音独立模块化

**当前状态：** Visual Agent 和 Voice 作为 Workflow 节点嵌入主链路，能力单一。

**模块化后：**

```
  Visual 板块 (独立微服务):
  ├── 商品识别 (已有) — 品类映射 + DB 精确匹配
  ├── 多图对比 — 拍两张商品, 对比规格/价格/外观
  ├── 包装信息提取 — OCR + NER, 识别成分表/配料表/生产日期
  ├── 穿搭视觉搜索 — 拍衣服→提取风格/颜色/版型→检索相似款
  ├── 肤质/发质检测 — 拍照分析皮肤状态→匹配护肤品
  └── 模型升级: qwen-vl-max → 本地小 VLM (InternVL2-2B)

  Voice 板块 (独立微服务):
  ├── 实时流式 ASR (已有) — 静音检测 + 文字清洗
  ├── 情感/语气识别 — 语调判断用户情绪, 调整推荐策略
  ├── 多轮纯语音对话 — 不依赖文字, 全程语音交互
  ├── TTS 个性化 — 多种音色, 语速自适应
  ├── 方言支持 — 粤语/四川话等高频方言 ASR
  └── 模型升级: qwen-omni-turbo → SenseVoice + CosyVoice
```

**架构变化：** 从 Workflow 节点 → 独立 gRPC 服务，主链路异步调用串入，不阻塞核心推荐流。

### 右下：记忆系统大规模化

**当前瓶颈：**
- context_snapshot 每次读写 PG，用户量增长后 DB 压力线性增加
- user_preference_entries 品类字符串匹配，条目增多后效率下降
- 对话历史全量存储，无归档策略

**优化方案：**

```
  短期记忆:
    context_snapshot → Redis Hash (hgetall/hmset)
    TTL 2h → 30min，Redis 持久化
    PG 写入降频: 每 5 轮或会话结束时批量写一次

  长期偏好:
    偏好条目 Embedding 化:
      每条偏好→向量→Qdrant user_preferences 集合
      新 query→ANN 搜索最匹配偏好→注入
      不再依赖品类关键词字符串匹配, 语义召回偏好
    协同过滤信号: 同品类用户偏好聚合→冷启动兜底

  会话记忆:
    对话按月份分区归档 (30天未更新→归档表)
    ContextCompressor 从简单摘要→用户画像向量增量更新
    每次对话后更新 user_profile_vec, 保留长期兴趣信号
```

## 附录 C · 答辩话术关键点

### 开场 (P1-P2)
> "OmniCart Agent 解决的不是'怎么搜商品'，而是'怎么决策'。用户只需要一句话或一张图，系统内部 5 个 Agent 协作完成从意图理解到可解释推荐的完整链路。传统搜索需要 10-20 分钟的决策过程，我们压缩到 3-5 秒。"

### Multi-Agent (P3-P4)
> "我们选择 LangGraph StateGraph 而非 ReAct，因为购物场景需要确定性的推理路径。5 个 Agent 各司其职，通过统一 WorkflowState 传递数据，每个节点独立容错。Router 和 Visual 有图片时并行执行，节省约 2 秒。"

### RAG (P5-P9) — 重中之重
> "RAG 是我们的核心引擎。不是简单的搜索+生成，而是 8 阶段流水线。口语查询先经过 LLM 改写，再向量化进入 Qdrant 双集合检索。产品级和分块级互补——产品级召回候选，分块级精准命中 FAQ 和评论中的细节。Reranker 精排后，三通道并行补充证据。最终编译为 250 token 的精简 Prompt，LLM 流式生成。全链路耗时 1-4 秒。"

### 记忆 (P10-P11)
> "三层记忆解决三个时间尺度的问题。FollowUpEngine 覆盖 7 种追问模式，用户说'第二个怎么样'能准确解析序数指代。长期偏好采用条目化管理，品类感知注入确保'油皮'偏好不会污染'手机'搜索。"

### 评分+安全 (P12-P13)
> "7 维评分每个维度都可追溯到证据 ID。幻觉防控四道防线确保推荐不说胡话——强制引用、品牌白名单、价格校验、超时兜底。"

### 收尾 (P14-P16)
> "OmniCart 不是又一个 AI 客服，而是完整的购物决策系统。从推荐到下单全链路自然语言驱动。Docker 一行部署，已上线阿里云。谢谢，欢迎提问。"
