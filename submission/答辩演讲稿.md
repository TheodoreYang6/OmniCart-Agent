# OmniCart Agent 答辩演讲稿

## P1 · 封面（30秒）

各位评委好，我是 OmniCart Agent 团队的代表。今天向大家展示的项目是——基于 RAG 的多模态购物决策智能体。

它的核心能力可以用一句话概括：**用户只需要说一句话或者拍一张照片，系统在 3 到 5 秒内，完成从意图理解、语义检索、证据评分到流式推荐的全链路推理，最终给出可解释、可溯源的购物建议。**

---

## P2 · 一句话→完整推荐（1.5分钟）

我们先看一个日常场景。

你想买一款蓝牙耳机，预算 500 以内。用传统电商搜索——输入关键词，翻列表，比价格，看评论，自己做决策。整个过程通常需要 10 到 20 分钟。

而用 OmniCart，你只需要对着豆仔说同样一句话："推荐一款蓝牙耳机，500 以内"。系统内部，5 个协作 Agent 自动完成品类识别、语义检索、多维评分，3 到 5 秒后，你看到的不只是一个商品列表，而是带评分、带证据、带推荐理由的结构化结果。你接着说"第二个加入购物车"，它就帮你加进去。全链路自然语言驱动。

这就是我们的核心差异：**不是帮你搜商品，而是帮你做决策。**

## P3 · 系统架构全景（2分钟）

这是我们的系统架构。

最上层是 Android 原生客户端，Kotlin 加 Jetpack Compose，四个 Tab——商品浏览、豆仔智能对话、购物车、个人中心。支持三种输入方式：文字、拍照识图、语音。

中间层是 FastAPI 后端，30 多个 API 端点。核心是一条 LangGraph StateGraph 编排的 Workflow 流水线——Router 做意图识别，Visual 做图像解析，Retrieval 做语义检索和证据补充，Reranker 做精排，EvidenceCheck 校验证据充足性，Decision 做 7 维评分，Response 做流式生成，Guard 做最终的安全守门。8 个节点，路径固定，状态显式，每一步都可追踪。

基础设施层是 PostgreSQL 管业务数据，Qdrant 管向量检索，Redis 做四级缓存。整套模型栈基于 Qwen 全系列——turbo 做意图和生成、vl-max 做视觉、embedding-v4 做向量化、rerank 做精排、omni-turbo 做语音。

整套系统 Docker Compose 四服务编排，一行命令部署，目前已跑在阿里云上。

## P4 · Multi-Agent 编排（2分钟）

这是我们五个 Agent 的协同设计。

首先要讲一个关键的架构决策：**为什么不用 ReAct？**

ReAct 是当前 Agent 框架的主流范式——让 LLM 自己决定下一步做什么。但购物场景有三个问题：调用链不可控、Token 消耗大、出问题难以定位。

所以我们选择 LangGraph StateGraph——有向图编排。流程是固定的，每个 Agent 只做一件事：Router 做意图和约束提取，Visual 做拍照识图，Retrieval 做三通道检索，Decision 做评分，Response 做回复生成。它们共享一个强类型的 WorkflowState 对象，各自只读写自己负责的字段——不会互相覆盖，不会出现状态污染。

右侧标注了我们和 ReAct 的对比：流程可预测、可调试、每个节点独立容错——一个节点挂了不会拖垮整条链路。

另外，这个架构有两个关键的性能优化：有图片时 Router 和 Visual 并行执行，节省约 2 秒；品类和子品类预填时 Router 跳过 LLM，只用规则解析，再省 1 秒。

## P5 · RAG 全链路总览（2分钟）

进入我们的核心模块——RAG 全链路。这是整个项目最重头的技术部分。

我用一个具体例子串完整条链路。用户说"推荐一款蓝牙耳机，预算 500 以内"——我们追踪这句话在系统中的完整旅程。

**第一阶段，搜索词构建。** 用户的自然语言不能直接拿去搜索——"推荐一款"是噪音，"500以内"需要变成数值约束。我们有两种路径：如果 Router 已经提取了品类、子品类和关键词，就走快速路径，直接拼接成"蓝牙耳机 真无线耳机 降噪 500元"，跳过 LLM，省 600 毫秒。如果信息不够，走慢速路径，调 qwen-turbo 做关键词改写，结果 Redis 缓存 30 分钟。追问场景品类已锁定，几乎都走快速路径。

**第二阶段，向量化。** text-embedding-v4 把搜索词映射成一个 1024 维的浮点向量。Embedding API 不可用时，回退到 jieba 分词加子串匹配。

**第三阶段，双集合检索。** 这是我们的核心创新。系统维护两套向量索引：product_chunks 分块集合约 800 条向量，每件商品拆成 10 到 11 块——一条 summary、一条营销描述、若干条 FAQ、若干条评论，每块独立 Embedding。优先在分块级别搜索，因为块级别的语义信号更纯粹——用户问"降噪深度多少"，FAQ 块"Q:降噪深度? A:40dB"的相似度可以达到 0.92，而整件商品向量中这个信号被稀释到只有 0.45。分块命中后按 product_id 分组聚合——summary 和 FAQ 权重 1.0，营销描述 0.9，评论 0.8。聚合结果不足时，用 products 产品级集合补齐。Qdrant 不可用，本地 Embedding 缓存暴力余弦；还没用，纯文本关键词兜底。

**第四阶段，多维过滤。** 品类不匹配的直接移除，价格超过预算的移除，子品类检索无结果时自动放宽重试。拍照识图的高置信度匹配商品这时候就置顶 0.99，用户偏好里的避雷标签匹配到的商品直接移除。

**第五阶段，Reranker 语义精排。** 每个候选商品构建一个结构化文档——标题、品类、营销描述前 300 字、前 2 条 FAQ、前 2 条评论、前 2 条证据片段。全部喂给 qwen3-rerank，和 query 做语义对比。分数出来后用固定校准公式——0.68 加 0.38 乘原始分——映射到商业可读区间。仅 1 个候选商品或快速模式下直接跳过，省 300 毫秒。Reranker API 异常就保持原始排序，不阻塞后续节点。

**第六阶段，三通道证据补充。** Text 通道是主通道，先执行。Review 通道和 Policy 通道用线程池并行跑——按照评分把评论分成风险、中性、好评三个等级，FAQ 标记为官方政策证据，confidence 给到 0.9。检索结果少于 3 件时，还会触发补充通道，用分块 Embedding 反向发现被遗漏的商品。

**第七阶段，上下文编译。** 这时候手里有 Top-K 商品、每条商品的评分、大量证据片段。但不能全塞给 LLM——会爆 token。编译器只取 Top 3 商品，每件只保留标题、品牌、价格、一条不超过 100 字的证据摘要。最终 Prompt 控制在约 250 token。完整的 Prompt 写入审计日志，供离线分析。

**第八阶段，流式生成加守门。** 正常走 LLM 流式生成，6 秒超时——超了就切结构化模板兜底。四种生成路径覆盖所有场景：闲聊走独立 Prompt，快速模式走纯模板，无结果诚实告知，正常模式 LLM 生成。生成后先做幻觉校验——回答必须包含候选商品的关键词，否则回退模板。然后 Guard 做 5 项安全检查，其中编造品牌和空结果瞎推荐是硬失败，直接拦截。

这就是完整的 RAG 8 阶段流水线。105 件商品、约 800 个分块、1024 维向量、4 级缓存、3 级降级，端到端 1 到 4 秒。接下来我拆解其中最关键的几个环节。

---

## P6 · 检索核心：双集合 + Reranker（2分钟）

这是全链路中最关键的两个环节：双集合检索和 Reranker 精排。

传统做法是每件商品生成一个 Embedding 向量——把标题、描述、FAQ、评论全部压缩到一个 1024 维向量里。这就是我们的 products 集合，105 条向量。但这里有一个问题：用户问"这个耳机支持 LDAC 吗？"——答案藏在某条 FAQ 里，但整件商品的向量中 FAQ 信息被稀释了，相似度不高。

所以我们引入了第二个集合——product_chunks。每件商品被拆成 10 到 11 个独立的小块：一个 summary、一个营销描述、若干条 FAQ、若干条评论。每块单独 Embedding。当用户问"LDAC 延迟多少"时，FAQ 块的向量和 query 的相似度可以达到 0.92，而产品级向量只有 0.45。这就是分块检索的价值——精准命中细节。

检索召回后，候选商品进入 Qwen3-Reranker 做语义精排。我们用一个固定的校准公式 `0.68 + 0.38 × 原始分` 把 Reranker 的分数映射到商业可读的区间。拍照识图的匹配商品直接置顶 0.99，避雷标签匹配的商品直接移除。

右侧可以看到最终效果——豆仔对话流里的商品卡片，每个推荐都是这条链路走完的结果。

## P7 · 证据补充 + 缓存降级（1.5分钟）

检索完成之后，还需要给每件商品补充证据。

三个通道并行执行：Text 通道是主通道，做语义搜索；Review 通道从用户评论中提取正向、中性、风险三级证据；Policy 通道从官方 FAQ 中提取政策证据。Review 和 Policy 用线程池并行跑，总延迟等于最慢的那个通道，而不是三个之和。

为了加速，我们部署了四级 Redis 缓存：视觉识别结果缓存 1 小时，搜索缓存 5 分钟，关键词改写缓存 30 分钟，完整工作流结果缓存 5 分钟。命中缓存的情况下，第二次相同请求几乎秒回。

更重要的是三级降级策略：Qdrant 不可用，自动切换到本地 Embedding 缓存，105 条向量暴力余弦相似度，毫秒级完成；本地缓存也不可用，回退到纯文本关键词匹配。每一层降级都是自动的、透明的，不影响用户体验。这就是系统的韧性。

## P8 · 评测体系（1.5分钟）

怎么验证 RAG 的效果？我们建立了检索评测加生成评测的双维度体系。

先说检索评测。5 项经典 IR 指标，基于 10 条 Golden Query，每条人工标注了哪些商品应该被召回。

Recall@5 和 Recall@10——前 5 个或前 10 个结果中召回了多少相关商品。计算很简单，命中的相关商品数除以总相关商品数。比如 query 有 3 件相关商品，Top5 命中了 2 件，Recall@5 就是 0.67。

MRR——第一个相关商品出现在第几位。取排名的倒数求平均。排名第 1 贡献 1.0，排名第 3 只贡献 0.33。这个指标惩罚"相关商品被埋在后面"的情况。我们当前 MRR 约 0.74，意味着平均第一个相关商品排在第 1.35 位。

NDCG@10——考虑排序位置的相关性得分，排名越靠前权重越大。折损因子是 log₂(rank+1)，所以第 1 位权重 1.0，第 10 位只有 0.29。再用理想排序下的 DCG 归一化。我们约 0.79，排序质量达到理想排序的 79%。

品类准确率——检索结果品类是否和 query 预期一致。10 条 query 中约 9.4 条品类正确。

P95 延迟——95% 的请求在 2.8 秒内完成。

10 条 Golden Query 覆盖 4 品类、多种查询类型——从条件筛选、场景化、模糊推荐到特殊约束和肤质匹配。

但检索评测只回答了"捞没捞到"。回答有没有编造信息？检索到的文档有多少是真正相关的？回答所需的信息是不是全在检索结果里？这三个问题检索评测回答不了。

所以我们新增了 RAG 生成评测——三项基于 LLM-as-Judge 的指标。

Faithfulness 忠实度：LLM 从生成回答中提取所有事实声明，逐条验证是否能在检索上下文中找到依据。有支撑的声明数除以总声明数。当前得分约 0.91。

Context Precision 上下文精准度：rank-aware 的平均精确率，检索回来的文档有多少真正相关，并且越相关排得越靠前越好。当前约 0.86。

Context Recall 上下文召回率：从标注数据中读取这个 query 应该覆盖的关键信息点，LLM 逐条检查是否在检索结果中被覆盖。当前约 0.82。

数据集是 105 条人工标注的 Golden Query，覆盖全部 4 品类、23 个子品类，关联 98 件商品。每条标注了相关商品 ID、相关度分级、以及回答应覆盖的关键信息点。

我们还做了参数网格实验——对 top_k、enable_rerank、context_products 三个关键参数做 24 组网格搜索，综合得分用 Faithfulness 0.4、Context Precision 0.2、Context Recall 0.4 加权。

## P9 · RAG 功能呈现 + 评分计算（1.5分钟）

RAG 链路的终点，用户看到的是一个带评分、带证据、可解释的推荐结果。接下来我逐维拆解这个评分是怎么算出来的——每个数字都能在源码里找到对应行。

**第一个维度，Relevance 语义相关度，权重 0.45。** 取值有一条优先级链：如果开了证据评分，直接用 Reranker 校准后的分数；没开的话看有没有 LLM 评估结果；都没有就 fallback 到关键词匹配。对中文做了 Bigram 特化——query 里的二字词如果命中了子品类名，每个加 0.10。比如"蓝牙耳机"的"耳机"命中了"真无线耳机"，加 0.10。

**第二个，Budget Fit 预算匹配，权重 0.20。** 价格在预算内按比例给分，远低于预算 0.98，接近上限 0.92；超出预算按超额比例梯度扣分，严重超出直接打到 0。无预算约束时给 0.98，几乎不影响排序。

**第三个，User Sat 用户满意度，权重 0.12。** 原始做法是评论均分除以 5，但"1 条五星好评等于满分"显然不合理。所以加了 Bayesian 平滑，虚拟 3 条评论，先验 0.80。再叠加评论数量微奖励和好评关键词加分。

**第四个，Value Score 性价比，权重 0.10。** 不同品类不能只用一套标准——耳机中位价 800，零食中位价 30，放一起比价格不公平。所以我们给 39 个子品类设了独立基准价和品质系数——零食的品质系数 1.4，说明一分钱能买到更多品质；手机的品质系数 0.9，说明贵有贵的道理。

**第五个，Spec Quality 规格品质，权重 0.08。** 有两条路径：如果 Router 已经提取了规格关键词，就匹配计数——用户明确提到的词权重 1.5 倍；如果没提取，就自动扫描描述文本里的规格信号——数字加单位、技术标记词、百分比、规格缩写，四类信号统计不用维护任何词库。

**第六个，Scenario Fit 场景适配，权重 0.05。** 12 个场景各有动态关键词库。"出差用的充电宝"自动匹配 flight 场景的关键词——航空、安检、登机、100wh。这个维度的权重只有 0.05，有场景时锦上添花，没场景时不惩罚。

**最后是加减分项：风险扣分，差评数超过 3 条加 0.08；偏好加成，匹配到用户偏好品牌加 0.08；避雷惩罚，命中避雷标签按置信度扣分。**

最终分数经 confidence_cap 压制，映射到 0 到 10 的展示分。右侧是 Android 端的评分拆解面板——7 条彩色进度条，每个维度标注了计算方法和证据 ID。

## P10 · 三层记忆架构（2分钟）

记忆系统是支撑多轮对话、个性化推荐和跨设备恢复的核心。三层架构解决三个时间尺度的问题。

**第一层，短期记忆。** 数据存在 conversations 表的 context_snapshot JSONB 字段里。每轮 SSE 响应结束后，系统写入本轮的用户查询、豆仔回复、推荐商品列表、Router 提取的品类约束。下一轮 Router 启动时，先查内存缓存——TTL 两小时、每五分钟清理过期条目——缓存没命中才读 PG。Router 把这些上下文注入 LLM Prompt，告诉它"上一轮用户在找什么""上一轮推荐了哪些商品""豆仔有没有在等用户回答"。

这里有个关键机制——merge_constraints 话题切换检测。如果本轮品类和上轮品类不一样，比如上轮搜 T 恤、这轮搜耳机，旧约束全部清空。如果本轮没检测到品类，也移除旧品类，防止"T 恤"这个标签锁死后续所有搜索。

短期记忆还维护了一个 pending_question 字段。每轮回复后，系统从豆仔的消息中提取问句——"要不要帮你推荐一些零食呢？"——写入 snapshot。下一轮 Router 检测到 pending_question 且用户回复的是"好"——19 个肯定词之一——直接把 user_query 替换为问题中的搜索意图。这不是让 LLM 猜，是规则级替换，确定性极高。

**第二层，长期记忆。** 存在 user_preference_entries 表里。我们选择了条目化设计——每条偏好独立一行，而不是一个用户存一个大 JSONB。每条有独立的 entry_id、category、brands、avoid_tags、budget 区间，还有 enabled 开关。这样用户搜"蓝牙耳机"时，系统只查 category 等于数码电子的条目，不会把"油皮护肤品"的偏好注入到手机推荐里。

品类感知注入的关键设计是 search_hints 和 context_prompt 的分离。品牌名和 must_tags 拼到 search_hints 里，直接影响检索召回。场景词和预算描述放到 context_prompt 里，只影响 LLM 的理解。"户外"场景关键词不会进入搜索词——防止用户查充电宝时，"户外"把充电宝挤下去推了手机。

长期偏好还支持从对话中自动提取。系统检测到"记住""以后都""一直喜欢"这类信号词，且没有"这次""临时"这类暂态词，就在后台异步调用 Qwen 解析用户消息、规范化字段、写入新条目。不阻塞 SSE 响应，用户当场看到推荐结果，偏好后台储存。

**第三层，会话记忆。** conversations 和 conversation_messages 两张表完整持久化对话历史。每条消息记录角色、内容、商品引用、证据引用。对话标题由 LLM 自动生成，要求八个字以内，失败就截取首条消息前 15 字。ContextCompressor 每轮异步做增量压缩，把多轮对话压成不超过 120 字的要点摘要，注入 Router 的后续推理。LLM 压缩失败时，简单拼接降级——系统总有一个可用状态。

三层记忆各司其职：短期管当前会话的上下文回溯，长期管跨会话的用户偏好，会话管完整对话的持久化和恢复。三层通过 FollowUpEngine 和 Router 协同——下一页我详细讲追问检测。

---

## P11 · FollowUpEngine + 偏好设置（1.5分钟）

记忆系统最核心的组件是 FollowUpEngine——统一的追问检测引擎。

它按优先级从高到低匹配 7 种追问模式：序数指代，比如"第二个怎么样"；品牌引用，比如"Sony 那个"；上次引用，比如"刚才那个能上飞机吗"；预算更新，比如"换成 200 以内的"；购物车意图，比如"加入购物车"；对比意图，比如"哪个更好"；模糊追问，比如"便宜一点"。

一旦命中，它自动继承上一轮的品类约束，定位目标商品，构建上下文提示，注入到 Router 的推理过程中。

还有一个关键设计叫问答链：豆仔在上一轮问了一个问题——比如"要不要帮你推荐一些零食呢？"——下一轮用户说"好"，Router 检测到 pending_question 的存在，自动把"好"替换为"推荐零食"，然后走正常的推荐流程。用户甚至不需要重新描述需求。

右侧可以看到 Android 端的偏好设置页——自然语言输入，LLM 解析，条目化保存，品类标签清晰展示。

---

## P12 · 7维可解释评分（1.5分钟）

推荐结果为什么排第一？每个分数都有明确的来源。

我们的评分公式是 7 维加权：relevance 语义相关度占 45% 的权重——这是最重要的，来自 Reranker 的分数，不是 LLM 的主观判断；budget_fit 预算匹配占 20%；user_sat 用户口碑占 12%，采用 Bayesian 平滑，防止"1 条 5 星就等于满分"；还有性价比、规格品质、场景适配，还有偏好加成和风险扣分。

每个维度的分数都绑定计算方法——method 字段——和支撑证据的 ID。比如 relevance 标注了 "reranker_score"，支撑证据是 "E-MKT-P001-0"。这意味着评审可以顺着证据 ID 追溯到原文。

右侧是 Android 端的评分拆解面板——7 条进度条，颜色编码，左边维度名，右边分数和权重。红色是风险扣分，绿色是偏好加成。不只是一个数字，而是一个完整的决策依据。

---

## P13 · 幻觉防控四道防线（1.5分钟）

AI 导购最怕什么？推荐不存在的商品，或者编造价格。我们设计了四道防线。

第一道，强制引用。LLM 的回答必须包含至少一个候选商品的品牌或标题关键词。如果它自由发挥没有引用任何商品——直接回退到结构化模板，不说胡话。

第二道，品牌白名单。维护 65 个已知品牌的列表，检测到陌生品牌直接标记 hallucination。

第三道，价格校验。回答中出现的任何价格，必须能追溯到候选商品的价格。编的价格过不了这一关。

第四道，超时兜底。LLM 流式生成有 6 秒超时限制，超时直接切模板返回。用户永远不会看到"正在思考中"然后什么也没有。

右边是 Response Guard 的五项检查。其中两项是硬失败——empty 结果却说"推荐你买"、编造了不存在的品牌——这两条一旦触发，回答会被直接拦截。

## P14 · Android 客户端全貌（1.5分钟）

这是我们交付的 Android 原生客户端。

四个 Tab：商品浏览，品类筛选加商品列表；豆仔智能，这是核心对话界面，SSE 流式打字机效果，支持文字、拍照、语音三种输入；购物车，增删改查加全选结算；个人中心，登录注册、地址管理、偏好设置、订单查询。

整套客户端 Kotlin 加 Jetpack Compose，MVVM 架构，Material 3 设计语言，30 多个 API 接入，Release APK 经过签名混淆只有 2.4MB。

后端 30 多个 API 端点、17 个路由模块、54 个单元测试。Docker 一行命令部署，目前跑在阿里云轻量服务器上，公网可访问。

## P15 · 竞品对比 + 技术亮点（1.5分钟）

我们把 OmniCart 和传统方案做一个对比。

传统搜索需要用户自己翻列表、比价格、看评论、做决策。传统 AI 客服只能套模板回复，说不出推荐理由，也无法操作购物车。

OmniCart 从输入开始就不同——文字、拍照、语音三模态。决策过程是 7 维可解释评分加证据溯源。交互支持多轮追问和指代消解。记忆系统覆盖短期、长期、会话三个层次。购物闭环从推荐到加购到下单全链路自然语言驱动。最后还有 Guard 和 Harness 双重安全验证。

底部是我们的 10 大技术亮点——从 LLM 查询改写、双集合向量检索、Reranker 精排，到三层记忆、四级缓存，再到 Android 原生全闭环。这些不是概念，每一个都有代码支撑，每一个都在当前的系统中实际运行。

## P16 · 后续优化方向（1.5分钟）

比赛虽然结束了，但我们对这个产品有更长远的规划。四个方向。

**第一，数据规模化。** 当前 105 件商品，目标是百倍千倍扩展。核心挑战是索引从静态全量变成增量实时更新——新品上架触发 chunk 拆分和异步 Embedding，评论新增追加 rev chunk 向量。Qdrant 按品类分片，查询先路由再检索。降级链要补一层中间方案，比如 Elasticsearch 稀疏向量或 pgvector，纯文本关键词放在最后。

**第二，全链路延迟从 3 秒压到 1.5 秒内。** 手段包括：Embedding 模型本地化部署，省掉 API 往返；Reranker 在 Top1 分数很高时跳过；Decision 完成后不等 Response 就开始 SSE 推送，用户感知延迟直接减 1 秒。

**第三，视觉和语音独立模块化。** 这两个能力目前作为 Workflow 节点嵌入主链路。未来拆成独立微服务——视觉板块补上多图对比、成分 OCR、穿搭搜索和肤质检测；语音板块增加情感识别、纯语音对话、方言支持。模型也从云端 Qwen 逐步迁移到本地小模型降本增效。

**第四，记忆系统应对大规模数据。** 短期上下文从 PG 迁移到 Redis Hash，减少 DB 写入频率。长期偏好 Embedding 化——每条偏好生成向量，用 Qdrant 做语义召回，不再依赖品类关键词的字符串匹配。对话历史按月分区归档，压缩器从简单摘要升级为用户画像向量的增量更新。

四个方向分三期推进：第一期延迟优化和增量索引，第二期视觉语音模块化，第三期记忆系统大规模重构。这个项目对我们来说不是一个比赛作品，而是一个持续打磨的产品。
