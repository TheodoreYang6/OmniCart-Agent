# OmniCart 全链路请求流程详解与性能优化分析

> 基于 2026-07 当前代码实测（三 flag 转正后：动态编排/LLM Planner/LLM Tool Calling 默认开启）。
> 所有耗时数据来自真实请求的 timing breakdown（冷缓存、本地 M 系列芯片、Qwen3-Embedding-0.6B 本地 + qwen3.7-flash API）。

---

## 一、完整流程：从用户查询到回答的 10 步

### 实测性能画像（先看全景）

一条冷缓存请求「推荐一款适合冬天用的保湿面霜」的真实分解：

```
总耗时 ~3.8s
├── router_ms:      1489  (39%)  ← LLM 意图理解，最大单点
├── planner_ms:        0         ← RulePlanner 规则模板，0 LLM
├── retrieval_ms:    255   (7%)  ← 多通道检索（本地 embedding + Qdrant）
├── rerank_ms:       246   (6%)  ← bge-reranker 本地 cross-encoder
├── evidence_check:    0         ← 纯规则
├── decision_ms:       6         ← 规则评分（LLM 关闭）
├── supervisor_ms:   507  (13%)  ← 动态图派发循环开销
└── response_ms:    1275  (33%)  ← LLM 生成（真流式，首 token 更早）
```

### Step 1｜请求接收（api/agent_stream.py `/api/recommend/stream`）

前端 `stream.ts` / Android `AgentStreamClient.kt` 发 POST（`StreamRequest`：message/user_id/
conversation_id/image_url/mode/fast_mode/exec_mode/deep_think）。后端立即返回
`StreamingResponse`（`text/event-stream`），随后所有产出以 SSE 帧推送：
`status`（中间态）→ `token`（逐字）→ `result`（全量 payload）→ `done`。

### Step 2｜入口预处理（同文件 gen() 内，检索前的三道门控 + 两个并行任务）

1. **快捷命令门控**：`_FAST_COMMANDS`（"看看购物车"等 5 条）→ 直接进工具链，不走 workflow
2. **购物操作关键词门控** → `ShopActionAgent`（见 Step 8 工具链）
3. **AGENT_LOOP 分支**（默认关）：开启时走 OmniAgent ReAct 循环（预算 3 轮 / deep_think 8 轮）
4. **并行预处理**（L413，`asyncio.gather` 双任务并发）：
   - `FollowUpEngine`：追问检测 → 产出 `enriched_query` + `followup_constraints`（预填约束）
   - `profile hints`：用户画像 → `avoid_tags`（如"敏感肌避免酒精"）
5. `product_focused_analysis` 模式（商品页"问问小O"）走独立分支：目标商品锚定 + 同类对比表

### Step 3｜Workflow 级缓存 + 选图（workflow/graph.py `run_workflow`）

- **Redis 缓存**：key = `query + image + user + session + exec_mode + context_prompt摘要`，
  TTL 内同请求直接返回（含 mode 防跨档串结果）
- **选图**：三 flag 转正后默认走**动态图** `router → planner → supervisor → reflect`；
  SSE 真流式用 `no_response` 变体（图跑到 decision 停，回答由 SSE 层边生成边推）
- 图为**启动期预编译单例**（`_compiled_dynamic_no_response`），请求期只 `ainvoke`
- 所有节点被 `_traced` wrapper 包裹（timing 兜底 + 异常 trace，观测不杀业务）

### Step 4｜Router Agent：意图识别与约束提取（agents/router_agent.py，1489ms）

- **视觉并行**：带图请求在 Router 起点就 `create_task` 并行调 Visual（qwen-vl），Router 完成后收割
- **两路解析**：
  - 规则解析 `_rule_based_parse`：正则抽预算（"300以内"）、品类词、人群词——0 延迟
  - **LLM 理解** `aunderstand_query`（qwen3.7-flash，已禁思考模式）：一次调用同时产出
    intent（封闭词表）+ constraints（category/budget/tags）——**这就是那 1489ms**
- **跳过条件**：`state.mode == "lite"`（原 FAST_MODE）或 FollowUpEngine 已预填约束 → 只用规则，0 LLM
- 产出写入 `state.intent` / `state.constraints` / `state.retrieval_plan`（channels/top_k）

### Step 5｜Planner + Supervisor：计划与派发（framework/orchestration/）

- **HybridPlanner 三层**：规则复杂度探测（multi_step/conditional/cross_domain 触发词）→
  简单 query 走 `RulePlanner` 意图模板（0ms，覆盖 90%+ 流量）；复杂 query 走 `LLMPlanner`
  （封闭 capability 词表 + PlanValidator 硬校验 + 进程内/Redis 双层缓存，失败降级规则）
- **Supervisor** 按 `ExecutionPlan` 逐步派发 capability（`framework/orchestration/capabilities.py`
  注册表按名查函数）；`tool:` 前缀步骤走 ToolRegistry；`MAX_SUPERVISOR_STEPS=16` 死循环护栏
- **Reflect**：步骤失败/结果不足时回炉重派（`reflect_count < max_reflects` 上限护栏）

### Step 6｜检索：QU 改写 → 向量化 → 多通道召回（255ms）

**6a. 关键词改写**（providers/recall/keyword_rewriter.py `llm_keyword`）：
- rich 路径：Router 已给出品类/tags 时**直接拼接不调 LLM**（大多数请求走这里）
- poor 路径：口语 query（"孩子上幼儿园用的杯子"）才调 LLM 改写成检索关键词

**6b. 查询向量化**（retrieval/semantic_retriever.py `_embed_query`）：
- 本地 Qwen3-Embedding-0.6B（1024 维），**非对称编码**：查询侧加 instruct 前缀，文档侧裸文本
  （V6 消融净收益 +3.2pt）
- Redis 缓存（key 带 `q1` 版本盐），同 query 重复请求零编码开销
- 本地模型单例双重检查锁 + encode 串行锁（MPS 并发前向无收益）

**6c. 多通道并行召回**（framework/retrieval/orchestrator.py 六阶段管线）：
- `text / review / policy` 等通道 = 注册的 RecallSource，`asyncio.wait` **并行 fan-out**，
  每源独立 `latency_budget_ms` 超时 + 总时间预算——单源慢/挂不拖累整体
- text 通道 → `search_chunked`：Qdrant ANN 检索 `product_chunks_v6_1024`（top_k×10 候选 +
  payload 服务端过滤 category/brand/price）→ 块按商品聚合（summary/mkt 取 max_score）→ top_k
- 结果 **RRF 融合**去重 + required 上抛 / optional 降级
- **三级降级链**：Qdrant → 本地 chunk 缓存余弦 → 文本子串匹配（任何一层挂了不空手）

### Step 7｜精排 → 证据 → 决策（246 + 0 + 6 ms）

- **RerankFusion**（providers/recall/rerank_fusion.py）：bge-reranker-v2-m3 本地 cross-encoder，
  只精排头部 8 候选；doc = 标题+品类+**召回命中块文本**（V6.1 修复：缺命中块信号时负增益 -20pt）；
  分数量化 0.05 噪声带 + 稳定排序（同档保留召回序）；Redis 缓存（d2 盐）
- **EvidenceChecker**：纯规则校验证据充分性，不足则标记 `sufficiency_report`
- **DecisionScoring**：规则加权评分（口碑/性价比/规格品质 component_scores →
  final_score/recommendation_level），`ENABLE_DECISION_LLM=False`——6ms 说明规则评分完全够用

### Step 8｜工具调用触发机制（购物车/订单等）

三个触发入口（优先级从高到低）：
1. **SSE 入口关键词门控**（Step 2）→ `ShopActionAgent`：
   `RuleToolRouter` 关键词匹配（"加购物车"→cart.add）→ 未命中且 `ENABLE_LLM_TOOL_CALLING`
   （已转正默认开）→ **LLM function calling**（`ToolRegistry.openai_schemas(llm_only=True)`
   投影给模型选）→ 都不中降级正常推荐
2. **Supervisor 计划内 `tool:` 步骤**：LLMPlanner 产出的多步计划（"查订单然后推荐类似的"）
3. **AGENT_LOOP ReAct 循环**（默认关）：LLM 自主决定调什么工具、循环几轮

统一执行 `ToolRegistry.invoke`：权限校验（order 档需 `_confirmed`，且 order.submit/pay/cancel
**永不进 LLM schema**——治理 CI 双保险）→ 弹性超时 → trace → Artifact 落黑板。
`shopping.search` 深检索工具内部复用 `run_capability_pipeline(["retrieval","reranker",
"evidence_check","decision"])` 子管线——工具拿到的商品与主链同质量。

### Step 9｜Response Agent：真流式生成（1275ms，首 token 更早）

- `no_response` 图跑完后，SSE 层直接调 `ResponseAgent.generate_stream(state)`：
  `chat_generation` 能力（qwen3.7-flash）`chat_stream` **逐 token yield → 逐帧 `_sse("token")`**
  ——LLM 产出即转发，用户感知延迟 = 首 token 时间而非全文时间
- prompt = 压缩上下文（top 商品+决策分+证据引用）+ FollowUpEngine 的 `context_prompt`
- **降级**：lite 档模板直出；LLM 超时（6s）/失败 → 模板兜底；空产出 → 兜底文案
- 断连检测：`raw_request.is_disconnected()` 每 token 检查，断了就停

### Step 10｜收尾：result 帧 + 后台持久化

- `result` 帧：answer + products + decision_results + evidence_list + trace_steps +
  timing + used_memories 等全量 payload（前端商品卡/追溯面板用）→ `done` 帧
- **后台持久化**：`asyncio.create_task` 落对话历史 + last_products 快照（供下轮指代消解），
  任务引用存 `_BG_TASKS` 防 GC——持久化不阻塞推流（fail-open）

## 二、性能瓶颈分析（按实测占比排序）

| # | 瓶颈 | 实测 | 根因 |
|---|---|---|---|
| 1 | **Router LLM 串行阻塞** | 1489ms (39%) | `aunderstand_query` 完成前检索不启动——但规则解析早已给出品类/预算，LLM 大部分时间在"确认"规则已知的东西 |
| 2 | **Response 生成** | 1275ms (33%) | 已是真流式（首 token 感知 <1s），全文时间受 prompt 长度与模型速度限制 |
| 3 | **Supervisor 派发开销** | 507ms (13%) | 动态图逐步派发 + 每步 trace/黑板事件，比静态图边直连多一层调度 |
| 4 | 检索+精排 | 501ms (13%) | 已优化充分（V6 + 缓存 + 并行通道），rerank 8 doc 逐个前向仍有 batch 空间 |
| 5 | 本地 embedding 并发排队 | 单请求不显 | encode 串行锁下，并发请求的查询向量化排队（正确性修复的代价） |

**非瓶颈**（已做对的事）：followup/profile 并行、visual 与 router 并行、多通道并行 fan-out、
查询向量/rerank/workflow 三层 Redis 缓存、图预编译、决策规则化（6ms）、真流式响应。

## 三、优化点与实施方案

### P0-A｜Router LLM 与检索投机并行（预期 -1s，最大收益）

**思路**：规则解析 0ms 就绪 → 立即用规则约束**投机启动检索**；LLM 结果回来后 diff 约束——
无变化（多数情况）直接复用检索结果，有变化才重检索。

```python
# _node_router 改造示意
rule_result = _rule_based_parse(state.user_query)          # 0ms
retrieval_task = asyncio.create_task(_speculative_retrieve(rule_result))  # 投机检索
llm_result = await aunderstand_query(...)                   # 1.5s，与检索重叠
if _constraints_changed(rule_result, llm_result):           # 少数情况
    retrieval_task.cancel(); state = await _node_retrieval(state)  # 重检索（仅 255ms）
else:
    state.retrieved_products = await retrieval_task         # 直接收割
```
**代价**：约束变化时浪费一次 255ms 的本地检索（便宜）。**风险控制**：先评测规则约束与
LLM 约束的一致率（预计 >80%），一致率达标再上线；宪法 §7 评测驱动。

### P0-B｜Router LLM 提速（与 A 叠加）

- prompt 瘦身：few-shot 例句压缩、输出 schema 收紧 + `max_tokens` 限制（意图+约束 JSON 很短）
- **意图语义缓存**：query embedding 余弦 >0.95 命中历史 (intent, constraints)——本地 embed
  20ms vs LLM 1.5s；口语电商 query 高度模式化，预计命中率可观（需实测）

### P1-A｜rerank batch 前向（预期 rerank -50%）

bge cross-encoder 支持 batch：8 个 (query, doc) 对一次前向替代逐对循环。改
`model_gateway` rerank 后端的推理循环即可，~20 行。

### P1-B｜embedding micro-batching（并发场景）

encode 串行锁下加 10ms 合并窗口：窗口内多个查询合成一个 batch 编码再分发——并发吞吐
提升数倍，单请求延迟只加 ≤10ms。

### P1-C｜Supervisor 派发瘦身

简单 plan（单步 retrieval→…→response 直线）识别后直接顺序 await，跳过逐步派发的
trace/黑板事件开销；复杂 plan 保留完整调度。预期 -300ms。

### P2｜其他

- **Response prompt 压缩**：证据只带 top3 商品各 2 条（现可能全带）——降首 token 时间
- **workflow 语义缓存**：近似 query（embedding 近邻）命中历史结果，加"改写确认"轻校验
- **decision LLM 保持关闭**：规则 6ms/效果足够，不要为"看起来智能"加 1s
- **降级链现状已完备，不动**：Qdrant→本地缓存→文本匹配三级、LLM→模板、Redis 挂→直算，
  且全部 fail-open（辅助通道永不反噬主链）

### 实施顺序建议

1. P0-B 意图语义缓存（纯增益零风险，先测命中率）
2. P1-A rerank batch（20 行，独立可测）
3. P0-A 投机并行（先跑规则/LLM 约束一致率评测，达标再上）
4. P1-B/C 视并发压力需求排期

## 🎤 面试版（30~60 秒口述）

> 我们的导购 Agent 是一条 LangGraph 动态编排链路：用户 query 进来先过两道轻门控（快捷命令、
> 购物操作走 function calling 工具链），然后 Router 用一次 LLM 调用同时产出意图和结构化约束，
> Planner 按复杂度分层——90% 的简单请求走零延迟规则模板，复杂多步请求才用 LLM 在封闭能力词表里
> 编排计划。检索层是多通道并行召回：本地 0.6B 模型做非对称编码，Qdrant 按商品知识块（营销/FAQ/
> 评价）ANN 检索加服务端过滤，RRF 融合后用本地 cross-encoder 精排——精排文档里拼了召回命中块，
> 这是我们评测驱动发现的关键修复，不然 reranker 反而负增益 20 个点。决策层是纯规则评分只要 6ms。
> 回答是真流式：图跑到决策就停，LLM 逐 token 产出直接转发 SSE，用户感知延迟是首 token 而不是全文。
> 全链路三层 Redis 缓存、三级检索降级、LLM 超时模板兜底，任何一层挂了都不空手。实测冷缓存端到端
> 3.8 秒，最大瓶颈是 Router LLM 的 1.5 秒，下一步方案是拿规则解析结果投机启动检索、跟 LLM 理解
> 并行重叠，预期能砍掉 1 秒。
