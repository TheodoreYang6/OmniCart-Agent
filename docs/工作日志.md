### 9. compare 目标分解：修复对比检索假阴性（灰度手测发现的真实 bug）

**问题发现**（动态编排灰度手测）：
- “索尼和Bose的耳机对比”→ 答“没有”——碰巧对（库内确无两品牌耳机，只有索尼相机/门锁、Bose手机/无人机等生成数据副产物）；
- “对airpods和huawei freebuds pro5做对比”→ 也答“没有”——**假阴性**：库内实际存在 p_digital_018 (AirPods Pro 3) 与 p_digital_007 (FreeBuds Pro 5)。
- 根因：① 整句双实体 query 单次混合检索，embedding 被“对比/耳机”主导稀释品牌信号；② “没找到”是 LLM 从 top-k 候选反推的臆断，非链路验证；③ rerank 前 8 门控使 9 位后的目标商品无法翻盘。

**修复方案**（全部在动态图，legacy 零改动）
- `planner.py`：`extract_compare_targets` 规则提取器（剥意图尾词 → 按 和/与/跟/还是/vs 切分）；compare 模板提得出目标时换用 `compare_retrieval` 能力 + `ExecutionPlan.meta["compare_targets"]`（新增 meta 字段）；提不出回退单路。
- `graph.py` 新 capability `compare_retrieval`：每目标独立子状态（model_copy）拼品类提示子查询 → `asyncio.gather` 并行检索 → 目标词命中标题/品牌才计命中 → **交替合并**（A1,B1,A2,B2…保证双方都进 rerank 前 8 窗口）+ 去重 + 证据同步过滤 → **per-target 命中数注入 context_prompt**（零命中显式标注“请明确告知无法对比”）→ 黑板发布 `compare.targets_retrieved` + trace step。
- 治理覆盖 compare 带目标分解分支；新增 6 例测试（提取器/模板分支/交替合并/零命中标注）。

**验证**：编排+动态图+A2A 30 例全绿；治理 `orchestration capabilities: [7]`；全量单测 **139 passed**（134→139）。待用户重跑灰度场景 4 确认真实环境效果。

**经验沉淀**：灰度手测的价值——“答对”不等于“能力对”：索尼/Bose 那条回答内容正确但机制靠运气（数据集碰巧无货），换一组库内存在的实体立刻暴露假阴性。对比类意图必须目标分解+逐目标验证，“LLM 看不到候选就说没有”是不可靠的否定。

**二次修复（用户真实环境重测仍假阴性，顺藤摸瓜找到三层根因）**：
1. **Router 合并吃掉 compare（主因）**：`HIGH_CONFIDENCE_INTENTS` 不含 compare，规则词库检到“对比”后被真实 LLM 的 recommend 覆盖 → compare_retrieval 永不触发（之前只修了 MockChat 侧，真实链路覆盖链仍在）→ 保护名单加入 `compare`；
2. **提取器句首 bug**：“对比airpods…”只剥“对”字产生广体 “比airpods” → 先剥句首引导词（对比/比较）再剥介词“对”；
3. **FollowUpEngine 污染**：追问场景 enriched_query 拼 "\n\n上下文" → 提取器只取首行。
新增测试：`test_compare_not_overridden_by_llm`（mock LLM 返 recommend，断言 compare 存活且品类增强仍生效）+ 提取器 3 新 case。全量 **141 单测 + 44 集成**全绿。
另：独立脚本跑 run_workflow 真实链路会卡死（uvloop/nest_asyncio 坑，与既有 pitfall 记录一致），改用 mock LLM 单测精准复现“LLM 降级意图”场景完成验证。
注意：workflow 级 Redis 缓存会留存修复前的错误答案（同 query 同 key），重测前需 FLUSHDB 或换词。

### 21. 增量索引 + Reranker 评测驱动修复

- **修复 2（噪声带稳定排序）**：cross-encoder 对同质候选（同品牌同品类多款）分差在噪声量级，直接按原始分排会无据换序 → 分数量化 0.05 档位、同档保留召回序（sorted 稳定性），只有显著更相关才提前 → faq/title 双双恢复 0.969/0.703（对召回零损害）

## 工作块 26：召回串味等四个结构性 bug 根治 —— 混合检索方案的评测证伪与真因修正

**用户反馈的四个 bug**：① 召回串品类（说面膜给面霜精华）② 列表出现同款不同条目 ③ 自然语言回答与商品列表不一致 ④ 下单流程规格选择按钮消失只能纯对话选。用户明确指向"不要只语义 embedding 检索，加入 BM25"。

**调研坐实的根因（全部实查）**：
- `providers/recall/keyword_source.py` 注册了 keyword 召回源，但其依赖的 `text_retriever.py` 首行自述"已移除 jieba，用 SemanticRetriever 替代"——**keyword 与 semantic 两路查同一份向量同一模型**，RRF 融合同源结果等于没融合
- 数据集 **81 组归一标题近重复**（威尔胜 NBA 比赛用球 3 条、探路者登山鞋同价同规格 2 条不同 product_id），检索层仅按 product_id 去重
- `context/compiler.py` L73 无图时只给 LLM 前 **3** 个商品，而 result 帧回传 5-20 个
- `cart.py` L191 产出 `sku_option` actions，但 `agent_stream.py` 仅 ShopAction 分支透传，**深度思考 Loop 分支 `_payload` 无 actions 字段**

**BM25 混合检索：实施 + 评测证伪（宪法 §7 数据说话）**
- 落地 `retrieval/sparse_encoder.py`（jieba 分词 + 型号整体保留"JBC-351"/"SK-II" + BM25 k1=1.2/b=0.75 + 语料统计落 `data/bm25_stats.json` + 统计缺失降级 idf≈1）
- Qdrant V7 双向量集合（`dense` 命名向量 + `bm25` 稀疏向量）+ `search_chunks(sparse=...)` 服务端 `Prefetch`×2 + `FusionQuery(RRF)`，hybrid 失败自动降级纯 dense
- **`scripts/migrate_v6_to_v7_hybrid.py`**：全量重建需本地 embedding 约 4 小时（V6 时期是 API 并发路径），改为 scroll 复用 v6 已有 dense 向量 + 仅补 sparse → **2 分钟完成 10066 点迁移**
- **四组对照评测**（新增 `scripts/eval_subcategory_purity.py`，20 例易混子品类专项）：

| 方案 | purity@5 | off_topic |
|---|---|---|
| dense + 块权重修正 | **0.82** | 2/20 |
| dense（基线） | 0.80 | 2/20 |
| hybrid + 块权重 | 0.78 | 2/20 |

3. **头像动画系统重设计**：原三处僵硬点 —— `ring-2 ring-brand-100` 硬边光环（深色下发脏）、表情靠条件渲染切换（零过渡的硬跳变）、`talking` 用 `animate-bounce-soft` 生硬上下弹。重做为：`.omi-ring` 伪元素柔和渐变描边 +（thinking 时）`.omi-ring-spin` conic 光环自转；`OmiFace` 改「新表情画底层 + 旧表情叠上层淡出」的交叉淡化（用 animation 而非 transition，因旧层是新挂载节点无初始值可过渡），只保留两层避免 9 个表情常驻 DOM；新增随机 3~6s 自动眨眼（`Eyelids` 毛色椭圆覆盖 + 眼缝线，比缩放眼睛本体更通用，因眼睛分散在各表情层内）；`talking` 换柔和呼吸缩放。

4. **首页猫猫趴在标题上（`OmiPerch.tsx`，3D + SVG 混合）**：
   - 素材：ImageGen 生成趴姿 3D 欧米。**首版踩坑**——要求"透明背景"时模型把棋盘格当图案画了出来（alpha 全 255），按纯灰判据抠图后猫周围留一圈被发光效果照亮的脏边，浅色主题下明显。改走影视工业标准路线重新生成**绿幕**素材（`G-max(R,B)=+110`，木板 `R-B=+80`，而猫身腮红仅 +44，分离度充足），抠图脚本 `scripts/cutout.py` 落 7 步：绿幕/木板双通道 → 区域生长清高光过渡带 → 全局木色收尾 → 形态学精修（填前景内部孔洞修鼻尖、opening 断细颈去碎屑）→ 下部暗边清理 → despill 去溢色 → trim。
   - **抠图连踩四坑**（均已在脚本注释固化）：对背景做 `binary_fill_holes` 会把猫当"洞"整只填掉；边缘清理阈值过宽会切断项圈挂环导致「只留最大连通域」把 omi 挂牌整块删除（故改面积阈值过滤）；木色区域生长不限行范围会把腮红吃成白洞；下部暗边清理不限「贴背景的边缘带」会挖掉胸口毛发阴影、不排除蓝调会把项圈吃成碎片。
   - **眼神跟随的实现取舍**：实测这只猫瞳孔是大面积均匀黑（占眼宽 64%），虹膜只剩细边 —— 移动瞳孔会立刻顶到眼睑，平涂 SVG 也盖不出 3D 虹膜渐变。故改为「用瞳孔同色圆擦掉 PNG 原静态高光 + 在跟随位置重画高光」：高光是眼神方向最强的视觉信号，且只在均匀黑区内操作，画质零损失。眼位/高光/瞳孔色全部来自对 `omi-perch.png` 的像素级采样（坐标写在 `EYES` 常量，换素材需重测）。
   - 交互：瞳孔高光跟随鼠标（rAF 节流 + 距离衰减 + 限幅 7px）、hover 抬头歪头、点击弹跳 + 三颗爱心从头顶上浮 + 眨眼、idle 极轻微呼吸（趴着的猫不适合浮空，故不复用 `xo-float`）。呼吸单独一层，避免与 lift/pop 的 transform 互相覆盖。
   - 定位用 `-mb` 负边距造重叠（而非 absolute），保持在文档流内避免标题跳位；实测 overlap 20px（矮屏 16px），中间垂爪正好压在「欧」字上沿。
   - 语义：改 `aria-hidden`（纯装饰彩蛋，品牌信息已由标题文字承载），不进 tab 序列。**顺带修正一个测试陷阱**：`Omi.tsx` 的 SVG 自带 `role="img"`，导致验收脚本的 `[role=img]` 选择器命中侧栏 logo 而非 perch，hover/click 断言假失败；改用 `data-omi-perch` 定位后全绿。

**36 补·终审补齐两项证据缺口 + 修复眨眼失效**：按 goal 审计口径逐条核对 spec §验收，发现两项证据不足并补齐，过程中暴露一个真实功能缺陷。

**缺陷（已修）：idle 态实际不会眨眼**。`Omi.tsx` 的 `blinkable` 把 `happy`/`smug` 一并排除（当初理由是「月牙笑眼本身已是闭眼形态」），但 `OmiAvatar` 的 idle 默认表情恰恰就是 `happy` —— 等于用户绝大多数时间看到的头像永远不眨眼，spec「idle 下随机 3~6s 眨一次」未达成，「让静态头像有生命感」的目标完全落空。改为只排除 `wink`/`sleepy`（这两个本身是闭眼语义，叠眨眼会破坏含义）。修复后实测 8s 内观察到眼睑出现。

同时修正验证脚本自身的一个假阴性：探针检测眼睑色写成了 `#E9E6E4`（那是 OmiPerch 的 LID 常量），而 `Omi.tsx` 的 Eyelids 用的是猫毛色 `CREAM=#FDF6EC` —— 两个 bug 叠加才让首轮「眨眼未观察到」的结论显得可信。

**补齐一：头像动画系统运行时验证**（此前只有代码审查与构建通过，属间接证据）。CDP 计算样式断言逐条对上 spec §三：

**36 补·尾巴摆动项的结论：不实现，并说明原因**。spec §四 列了「尾巴：SVG path + CSS keyframes 左右摆动，hover 时频率加快」。该条写于素材生成之前，假设主视觉里有可见尾巴；实际生成的趴姿素材中尾巴被身体完全遮挡（右侧那团经放大确认是蜷曲的后腿爪掌，不是尾巴），无可动对象。

按 fidelity 要求做了两轮真实尝试（均在轮廓外新增 SVG 尾巴、置于 PNG 之下使尾根被猫身遮挡，功能断言全部通过：`omi-tail-wag` 2.6s、hover 加速至 0.9s、reduced-motion 下 none）：
- 第一版（奶白→浅蓝→品牌蓝饱和渐变）：扁平色带与 3D 毛绒质感硬冲突，实拍像糊上一条蓝缎带，且尾根衔接处有硬边
- 第二版（贴猫毛白 + feGaussianBlur 软化边缘）：浅色主题下完全隐形（白尾巴压浅底），深色主题下变成一块像漏光污点的白斑

两版都无法同时满足「可见」与「协调」，而用户对本次改造的硬约束是「一定要协调」。故撤除该实现（代码与 CSS 均已清空，`grep omi-tail` 零残留），不以牺牲画面协调为代价换取字面达标。该条的产品目标（让猫动起来、有生命感）已由 idle 呼吸、眼神跟随、随机眨眼、hover 抬头歪头、点击弹跳+爱心五项达成。若确需真尾巴摆动，需重新生成一张尾巴外露的姿态图，届时可直接复用已验证过的分层方案（尾巴 SVG 层置于 PNG 之下 + `transform-origin` 定在尾根）。
