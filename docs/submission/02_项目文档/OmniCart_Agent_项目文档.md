# 欧米 · OmniCart Agent 项目文档

## 1. 目标与边界

欧米是面向购物场景的多模态智能体。它不是只返回商品列表的搜索系统，也不是自由聊天机器人，而是围绕“理解需求、找到商品、核对差异、给出建议、完成交易”设计的受控决策系统。

当前支持的主要能力：

- 自然语言推荐、组合选购与多目标需求拆分；
- 品牌、型号、指定商品的精准解析；
- 图片识别后的商品理解与检索；
- 单品深度档案与同类横向对比；
- 购物车、库存、订单、偏好与连续会话；
- 常规推荐与深度思考两种体验模式。

### 身份与数据边界

系统面向两类身份：

- **游客**：获得一次性推荐，不创建或写入会话，不读取或写入偏好，不保留购物上下文；
- **登录用户**：通过受认证身份恢复会话、使用偏好，并可使用购物车、订单等能力。

请求体中的 `user_id` 不作为可信身份来源。Web 端使用 HttpOnly Cookie（`omnicart_session` / `omnicart_guest`），Android 端复用登录 Bearer Token，服务端只使用解析后的身份；`allow_legacy_user_id` 默认关闭。

## 2. 总体架构

```text
Web / Android
    ↓ SSE / HTTP
FastAPI 接口层
    ↓
LangGraph 工作流与受控 Agent Loop
    ↓
Router / 实体解析 / 工具运行时 / Guard
    ↓
PostgreSQL · Qdrant · Redis · 模型网关
```

一次推荐的标准交付链路：

```text
Query / 图片 / 商品点击
→ 需求理解与实体解析
→ 受控工具调用
→ 商品候选、证据与推荐简报
→ 回答安全校验
→ 阶段进度、商品卡片、真实流式回答
```

系统将商品主数据、会话事实、商品身份与偏好等结构化数据保存在 PostgreSQL；将商品文本块的语义向量保存在 Qdrant；Redis 与本地缓存用于短期检索复用。Embedding、Reranker、文本生成和视觉能力通过统一模型网关调用，支持超时与降级。

当前数据基线：8 个一级品类共 1000 件商品，包含规格、FAQ、评价与派生字段；默认启用 V9 Chunk 检索（`product_chunks_v9`）。

## 3. 双模式 Agent 工作流

### 3.1 常规推荐

常规推荐以稳定与速度为优先。Router 先生成结构化需求计划，再运行一次受控的 `shopping.search` 检索批次；如果用户目标包含多个独立商品需求，则在同一批次内按组分别检索。之后依次完成候选过滤、推荐简报、Guard 校验和流式回答。

### 3.2 深度思考

深度思考使用有限轮次的 Plan-Execute Loop。模型先生成可执行待办，再按需调用检索、单品档案或比较工具；每轮工具结果写入独立账本，由运行时判断是否仍有信息价值。

深度模式并非无限循环。当前工具策略限制模型决策轮次、商品检索次数和比较次数；当目标已覆盖、出现重复调用或预算耗尽时，系统强制收敛。用户只会看到“理解需求、挑选商品、核对依据、整理建议”等友好阶段，不会看到思维链和工具参数。

## 4. Harness：受控 Agent 的工程护栏

欧米将 Agent 质量控制放在独立 Harness 中，而不是完全依赖提示词。

- **调用前控制**：校验工具 Schema、参数类型、用户权限、商品锁定范围、调用预算和重复检索。
- **调用后归并**：工具只返回状态补丁；候选组、证据、档案和失败原因按调用顺序合并，后续调用不能覆盖已成功的独立需求组。
- **停止策略**：已覆盖全部目标、没有新信息价值、模型重复调用或预算耗尽时停止 Loop。
- **结果 Guard**：检查商品范围、价格、证据、风险提醒、需求组覆盖和健康表述，生成 `harness_report` 供诊断与评测。

这种设计把“模型可以决定下一步做什么”与“系统决定什么可以做、做到何时停止”分开，减少多轮工具调用中的跑偏和空转。

## 5. 工具体系与业务边界

工具通过统一注册表、参数 Schema、权限等级和结果协议接入运行时，共 22 个：

| 工具族 | 工具 |
| --- | --- |
| 购物车（5） | `cart.view`、`cart.add`、`cart.remove`、`cart.update_qty`、`cart.clear` |
| 订单（7） | `order.preview`、`order.submit`、`order.list`、`order.detail`、`order.cancel`、`order.track`、`order.pay` |
| 购物核心只读（6） | `shopping.search`、`shopping.display`、`shopping.detail`、`shopping.product_dossier`、`shopping.compare`、`shopping.check_inventory` |
| 偏好（3） | `preference.save`、`preference.list`、`preference.delete` |
| 会话（2） | `conversation.history`、`conversation.reset` |

关键边界：

- `shopping.search` 负责发现候选，服务于推荐、同类搜索和未锁定需求；
- `shopping.product_dossier` 只在商品已唯一锁定后读取规格、FAQ、评价、风险和证据；
- `shopping.display` 显式声明最终展示的商品，保证回答与卡片一致；
- 指定商品、问欧米和图片识别命中唯一商品时，系统优先锁定该商品并使用 dossier，不允许泛检索把主体冲淡。

### 5.1 购物车 / 下单交互设计

交易类工具不仅返回文本，还返回结构化 `shop_card` 与按钮动作，前端按类型渲染卡片：

| 场景 | 结构化结果 | 交互 |
| --- | --- | --- |
| 单规格加购 | `cart_summary`（本次商品 + 购物车总件数/合计） | “去购物车结算”按钮 |
| 多规格加购 | `sku_picker`（商品 + 规格列表） | 规格选项按钮，点击直连加购 |
| 下单预览 | `order_preview`（明细、合计、地址） | “确认下单 / 修改地址”按钮 |
| 下单成功 | `order_created`（订单号、合计、预计送达） | “查看订单”按钮 |

下单预览与下单成功两步会由模型依据同一份 `shop_card` 数据生成流利的收尾文案（接地 prompt，禁止编造订单号、金额与送达时间）；模型异常、超时或空结果时回退到确定性模板。加购与规格选择保持确定性模板，避免拖慢高频操作。

## 6. V9 检索与 RAG

V9 检索的核心思想是“先让不同信息以合适粒度参与语义匹配，再按商品而不是按文本块交付”。每件商品被拆成以下 Chunk：

- 身份：标题、品牌、型号、品类、SKU；
- 事实：可回溯的规格与结构化属性；
- 商品说明：按语义边界切分的营销文本；
- FAQ：一问一答的官方信息；
- 评论与评论主题：原评和带引用的主题聚合。

每一次 `shopping.search` 都是一次独立、可追踪的检索过程：

```text
工具 Query + Router 子目标
→ 一次 Query Embedding
→ Top 100 多视角 Chunk 召回
→ 按商品 ID 聚合 Top 24
→ 本地 BGE Reranker 压缩 Top 12
→ 闭集 LLM Filter
→ 并行整理证据包
→ 输出受控商品结果
```

普通语义需求使用 Dense 检索；品牌、型号、SKU、罕见规格等明确词面需求启用 Dense 与 BM25 的 RRF 融合。类目和预算等可验证条件可以下推过滤；模糊子类不会被错误当作数据库精确条件，从而避免零召回。

### 6.1 评测数据（口径说明）

以下指标来自仓库内已发布的检索评测（`data/rag_eval_runs`，tag=`v7_release`，集合 `product_chunks_v6_1024`），用于说明检索链路在已发布评测集上的表现；当前默认索引为 `product_chunks_v9`，评测集可随新索引迭代复跑：

| 评测 | 用例数 | 指标 | 结果 |
| --- | --- | --- | --- |
| FAQ 检索 | 64 | hit@1 / hit@5 / mrr@10 | 96.9% / 98.4% / 97.4% |
| 标题检索 | 64 | hit@1 / hit@5 / mrr@10 | 73.4% / 95.3% / 84.5% |
| 检索纯度 | 30 | purity@5 / 库存修正纯度@5 | 90.7% / 94.7% |

批次耗时：128 例检索评测约 6.2s（批内单例约 48ms），30 例纯度评测约 7.0s，均为本地推理环境下的可复现数据。

## 7. Router 与闭集 LLM Filter

Router 将自然语言转化为结构化计划：意图、独立检索组、预算、必须条件、偏好、避雷项、证据关注点和回答目标。

例如“想买好吃又好喝的，但不想太有负担”会形成零食与饮品两个独立组。每组保存自己的 Query、候选、证据、失败原因和最终商品，避免其中一组在后续检索或回答中丢失。

LLM Filter 不负责从全库找商品，而是在每组经聚合和 Rerank 后的 Top 12 闭集候选中做决策，输出主推、备选、条件推荐、排除项和缺失原因。服务端会复核返回的商品 ID、预算和候选范围；模型输出非法、超时或不可用时，系统按已验证的排序稳定降级。

## 8. 精准解析、单品档案与横向对比

商品身份层保存品牌、产品线、型号、规格键和别名，用于识别“iPhone”“苹果 15”“iPhone15 Pro”等非标准表达。解析结果分为精确商品、商品系列、歧义和未命中四类：精确商品锁定主体，系列只在系列内交付，歧义时先澄清而不替用户猜测。

单品 dossier 将主商品、规格、价格、FAQ、评价概览、风险、信息缺口与证据 ID 整理成结构化档案。完整档案留在服务端，模型只接收稳定且受控的摘要。

横向对比使用独立链路，而不是普通推荐的附属排序：

```text
锁定当前商品
→ 严格同子类候选
→ 去除同款与重复版本
→ 覆盖低价、相近、升级价格带
→ 为每件商品建立 dossier 与事实表
→ LLM 在闭集内给出条件化裁决
→ 对比卡 + 真实流式建议
```

对比不会用“评价数量更多”直接选赢家。当没有脱离场景的绝对优胜者时，模型必须明确说明不同商品分别适合什么情况。卡片展示价格、已核对维度、注意点和“怎么选”，图片统一使用稳定的商品图片 API 兜底。

## 9. 评分、证据与回答一致性

系统不再把单一推荐分数当作商品绝对质量。内部将三类信号分离：检索排序、LLM Filter 裁决和证据状态；对用户则展示当前需求下的适配指数、匹配等级、适合原因、购买前注意点和资料状态。

最终交付由推荐简报统一约束：主推最多三件、备选最多六件，正文、卡片、证据和评分都只能引用受控范围内的商品。对比场景则使用专门的事实表与条件化结论，避免一般推荐分数干扰比较。

## 10. Context 与 Memory

会话原始消息是权威事实源，检查点是可重建、可版本化的上下文投影。检查点保存当前购物目标、已确认约束、已否决条件、锁定商品、已推荐商品、待确认问题和话题切换状态。

最终回答模型只通过 `ConversationContextAssembler` 接收一份 `AnswerContext`：

```text
本轮问题与计划
→ 已确认会话状态
→ 最近完整对话
→ 本轮推荐简报
→ 单品档案与必要证据
→ 相关长期偏好 / 图片识别结果
```

工具原文、ReAct scratchpad、过期候选、未校验草案不会进入最终回答上下文。上下文使用分区 Token 预算：当前请求、锁定商品和首选卡优先保留，较旧历史和次要证据优先裁剪；`ContextManifest` 记录来源和裁剪原因，便于审计。

## 11. 流式交付、可观测性与质量验证

前后端使用统一 SSE 协议，事件顺序为：

```text
stage → recommendations / focus_analysis / comparison → token → result → done
```

| 事件 | 用途 |
| --- | --- |
| `stage` | 用户可理解的阶段与文案（understanding / searching / comparing / checking / answering） |
| `recommendations` | 常规推荐的已校验首选/备选、决策标签与证据 |
| `focus_analysis` / `comparison` | 问欧米单品档案 / 横向对比结构化数据 |
| `token` | 自然语言回答的真实流式文本 |
| `result` | 当前轮完整结果（商品、决策、证据、`shop_card`、`actions`、`harness_report` 等） |
| `error` / `done` | 异常与完成状态 |

商品候选锁定后先发送卡片，随后发送真实模型 token，最后发送完整结果与诊断摘要。客户端只呈现一个动态过程状态，不堆叠内部执行步骤。

### 11.1 测试与质量门禁

- 后端：34 项单元测试通过，覆盖认证、地址、购物车仓库、聚焦/对比逻辑、购物文案与订单总结 prompt 等；`compileall` 全量编译通过。
- 前端：51 项测试用例通过，`tsc --noEmit` 与 `eslint --max-warnings=0` 通过。
- 工程治理：`importlinter.ini` 对分层依赖做物理约束，`schemas` 保持纯契约。

## 12. 设计取舍与总结

欧米的核心不是“让大模型直接推荐商品”，而是用 Router、检索、工具、事实、上下文、Guard 和流式交付共同构成一个受控购物决策系统。模型负责理解、选择和表达；系统负责边界、事实、状态、校验与可靠交付。

主要取舍：

- 用确定性推荐简报换取卡片与正文一致，而不是让模型自由发挥；
- 用受控工具运行时换取可审计的交易闭环，而不是让模型直接写库；
- 用“先卡片后文字”的交付顺序换取用户在流式生成前即可决策。

本地体验、环境配置与验证步骤见 [体验与部署指南](OmniCart_Agent_体验与部署指南.md)。
